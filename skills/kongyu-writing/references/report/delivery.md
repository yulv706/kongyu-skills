# 报告交付：格式、双层读者与检查

适用：决定报告用什么形式交付，以及 HTML 报告的交付检查。内容怎样写见各文体 ref。

## 选择交付形式

用户要什么形式，就给什么形式。未指定时，选能解决读者障碍的最小形式：

| 需求 | 形式 |
| --- | --- |
| 当前聊天能回答 | 聊天回答，不生成文件 |
| 实质报告或决策备忘 | Markdown 源层 |
| 用户要能打开、分享、给人看 | Markdown 源层加派生 HTML |
| 用户要 DOCX 或 PDF | 源层正确后，用对应文档技能 |
| 用户要 PPT | 交给 `kongyu-ppt`，不把报告自动当成幻灯片 |

普通中间进度不生成 HTML、PPTX 或 DOCX，除非用户要报告或阶段收口。

## 双层读者

| 层 | 形式 | 目标 |
| --- | --- | --- |
| 源层 | Markdown、JSON、CSV、日志、来源记录 | 机器可审计：事实、口径、来源齐全，不加装饰 |
| 读者层 | HTML、PDF、看板，从源层派生 | 人能读懂：结论先行，判断和证据邻近，细节在后 |

规则：

- 数字、标签和证据先在源层落地，再生成读者层。
- 读者层不能出现源层没有的声明。
- 源层事实错了，先改源层，再重新生成读者层；不手改 HTML 掩盖旧数据。
- 原始来源、运行编号、哈希放在源层或附录，不作为读者的主阅读路径。

## HTML 交付

HTML 报告的结构由 `references/report-shells.md` 的 Self-Contained Chinese HTML 一节确定。视觉、布局、字体和响应式由 `kongyu-surface` 负责。

交付前确认：

- 从权威源层生成，而不是手改。
- 能用本地 `127.0.0.1` 地址直接打开，服务只指向专用的清洗目录，并记录进程号和端口。
- 中文外壳，第一屏能独立说明这是什么、结论是什么。
- 长表格、原始日志和标识符放在主判断之下。
- 限制贴着它限定的结果；全文末尾的边界只保留仍会改变总体判断的部分。
- 有目录或锚点导航时，章节 id 稳定，名称用读者的任务，不用内部阶段名。
- 图和脚本、资源本地打包，不走 CDN 动态加载。JS 图通过本地 HTTP 服务渲染。

不默认加一键导出按钮。普通浏览器打印仍不可读时，才与 `kongyu-surface` 商定。

预览用完即停：核对进程号、端口和命令身份后再停止，并验证端口已关闭。用户要保留的产物不删。

## 硬链接安全编辑

部分工作区文件是 Windows 硬链接，原生编辑工具的临时文件加重命名会断开链接。

编辑前检查 `fsutil hardlink list <file>`。若返回多条路径，用 Python 的 `write_text` 或 `Set-Content` 原地写入，不用临时文件重命名。编辑后再检查链接和同组文件的哈希。

## 读者标签

读者面向的标签使用读者的词，不用内部字段名：

- 差：`entry 行`、`fetch rows`、`v2 baseline`、`gate`、`high_quality_or_probable`
- 好：`已检查的记录`、`尝试打开的页面`、`旧数据底座`、`质量门槛`、`可能进入分析的页面`

需要保留内部字段时，放在括号或附录里。

## 面向现有项目的看板

先沿用项目既有的视觉语言、导航、密度和词汇；只改善比例、层级和一个有理由的细节，不换成营销页或新的设计体系。

- 用行、列表和分段，减少嵌套卡片和装饰性边框。
- 框只用于真实边界：证据表、表单、错误、上传区、媒体预览、诊断。
- 一个去处对应一个点击目标。

每个指标卡回答一个读者问题：数的是什么，口径与分母，比较对象与方向，数值与不确定性，差异支持什么、不支持什么。一张卡不同时放很多独立数字。

## 交付前的读者检查

把报告当成聊天记录已被删除，重新读一遍。以下任一项不通过，就重写：

- 第一屏有术语需要先读前文才懂。
- 数字在单位说明之前出现。
- 读者看不出报告支持哪个决定。
- 内部名称比读者的概念更醒目。
- 状态类报告只给文件路径，没有说明现状。
- 没有下一步。
- 长 HTML 报告缺少找到章节所需的导航。

## 报告边界

- 密钥、cookie、私有认证地址、完整连接串、内部临时目录、未发表草稿和私有过程文件，不进读者面向的报告。
- 引用前先分类：已发表来源、内部原型、本地演示。内部原型和本地演示不是外部证据。
- 数字来源：Token、资源用量等数字必须来自实际系统、API 或日志，或明确标注为估算。
- 新结果到来时整体重写：核对受影响的判断，用全部当前结果重排首屏、正文、表、边界和决定，删除失效内容。不追加“更新”段，除非用户要审计历史。
- 用户要“案例”时，交付可以粘贴的真实任务提示：做什么，用哪些工具或命令，验收标准是什么。不交自验证的演示脚本。

## 读者说“没看懂”

读者说没看懂，是成稿失败，不是读者的问题。按下面做：

1. 找到读者卡住的第一处：哪句话、哪个表头、哪个数字需要内部背景才能懂。
2. 用材料里的对象、动作和结果，重述三问：做了什么，发现了什么，要决定什么。
3. 补上第一个缺失的前提，解释指标的单位、分母和对照。删掉不支撑判断的内部过程，不追加解释补丁或免责声明。
4. 核对改前改后的事实、例外、条件、数字、要求强度和不确定性。
5. 找一位没读过材料的读者，只让他复述三问，并指出仍接不上的地方。未通过就继续改。
